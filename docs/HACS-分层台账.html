一、这份台账怎么用

本文件是《HACS 分层规划》的阶段 0 产出，是层归属与门禁基线的唯一权威版本。 规划文档（docs/HACS-分层规划-handoff.html）回答「该怎么分、为什么这么分」；本台账回答 「现在每个件实际站在哪一层、依赖谁、踩了哪条判据、怎么复查」。动结构之前先对台账， 偏离先升版本再动码。

1.1 三个口径

  • 层归属是人判的，不是推的。判断法则沿用规划文档：通信层四节点对等、业务层中枢独有。 一个件若同时干两层的活，台账里记两个层并打 拆分点， 不为它硬凑一个层。
  • 数字全部来自实测，可复跑：件数/行数 来自 wc -l；门禁四项来自 python tools/check_layers.py；进程与启动方式来自本机进程与计划任务实查。 标注 会漂移 的，落地前复核。
  • 提示级 vs 硬级。只有「依赖方向」是硬门禁（退出码 1）。业务词、宿主硬编码、存储句柄 是提示级：它们的命中必须人判（注释里提到「会话」不算越层，真去读别人库算）。 退出码 2 = 源码树守卫：源文件缺失超过一成时判「查不了」，不给假绿灯 （对外仓里只有层归属表、没有源码，跑出来会是「件数齐全、零违规」——那是假象）。

1.2 台账的机器可读孪生体

本文件的所有表格由 tools/gen_ledger_doc.py 从 tools/hacs_layers.json 生成。要改层归属，改 json 再重跑生成脚本，别直接编辑 HTML 表格 —— 否则文档与门禁读的那份口径分家， 门禁就白跑了。

三、依赖方向实测（门禁检查 1）

结论：现有 import 图与五层方向一致 —— 零反向依赖。 这不代表解耦没问题，而是说明耦合不长在「谁 import 谁」上。真正的越层是三处： 语义越层（业务词长在通行层）、句柄越层（通行/适配件直读别人的库）、配置静态（改动靠改文件+重启）。 后两处见第四、七节。

3.1 判据与门禁规则

  • 允许方向：L4 → L3 → L2 → L1 → L0（上层依赖下层）；同层可互依； 横切 X 可被任意层引用；工具面 T 不受限（不属运行路径）。
  • 组合根 C（进程入口装配）排在方向序列最前：C 可 import 任意层，任何层不得 import C。 判据逻辑无需特判 —— C 的 rank 最小，rank[src] <= rank[dst] 天然成立/天然违规。 它的用途是给「反向依赖」一个合法出口：把注入动作放进进程入口，而不是让下层去 import 上层。
  • 反向依赖（下层 import 上层）= 硬违规，退出码 1，必须改。
  • 工具面缺席会让结果失真：ledger_patrol.py 这类巡检件 import 域件是正常的， 把它当运行件就会报假违规。

3.2 基线（件数 / 层间 import 边 / 方向违规 —— 由 check_layers.py 实时打印后手抄，非随生成重算）

指标实测含义
登记件数65运行件 + 工具件，不含测试
层间 import 边52跨层引用（含共用底座件）；同层内引用不计
方向违规0硬门禁今日通过

层间 import 边从早期基线的 17 涨到 52，不是「耦合变多」，而是解耦的账单： 把原先各自复制的底座提到唯一出处之后，每个调用点都得 import 一次 —— L0 node_paths.py（≈19 件引用，按 grep -l 计）、L1 web_gateway.py（5 件）、 横切 view_auth.py（5 件）、L2 agent_usage.py（4 件）四类底座正是边增长的主要来源。 反过来，件与件之间真正的主战场仍不是函数调用：端口、文件、数据库、启动参数这四类通道不写一行 import 也能把两个件焊死，所以解耦必须在契约层收口。数字会漂移，落地前以当次 check_layers.py 的输出为准；第四章的硬编码 / 存储句柄各组数字为刀 3 时点实测，重算要跑各自脚本。

未入网成员一次性邀请码申请注册 / 查询进度 / 取引导包最低：只能证明「有人给了我这串码」
待批准成员自持私钥签名查询进度 / 取引导包 / 自报上线中：身份已登记，尚未授权
已入网成员自持私钥签名正式通道 + 名册只读高：按角色模板授权
管理员既有账号体系（横切身份）批准 / 驳回 / 吊销 / 名册全量最高：不新造一套，复用现有实现

端点方法用途幂等性

6.3 数据形状（三个关键结构）

结构字段说明
注册请求成员标识 · 公钥（ed25519）· 节点提示 · 声明能力 {后端类型, 模型, 工具体} · 客户端版本 · 邀请码没有私钥、没有口令。声明能力只是「自称」，不据此授权
签发结果成员标识 · 通道参数 {模式, 端点, 主题前缀, 角色模板} · 同伴信息 · 引导包 {地址, 校验和, 版本, 有效期} · 签发时间 · 有效期通道参数里只有角色模板名，没有口令 —— 口令由成员侧用自持私钥向通道换取
引导包通行层客户端件 · 本成员档案片段 · 自启模板 · 校验和清单一次性 + 短时效 + 绑公钥。包内含模板不含生产凭据

6.4 七条硬约束（逐条可校验）

#约束怎么校验
1私钥永不出机：成员本机生成密钥对，只上报公钥注册请求体里搜不到私钥字段；抓包/日志里无私钥头标记
2数据面与控制面分离：控制面不可用时，已在网成员通信不受影响停掉注册服务，跑一轮既有成员的点对点与群发，应全通
3幂等注册：同 (成员标识, 公钥) 重复申请返回同一身份连发两次申请，比对受理号与最终签发结果一致
4授权与登记分离：登记 = 身份落库；授权 = 通道侧按角色模板放行登记后未授权时，通道应拒绝其连接（而非接受后不投递）
5吊销即时生效于新连接，已建立连接在下一轮重连时失效吊销后立刻发起重连，应被拒；旧连接的下一条消息应失败
6引导包一次性：过期/重复取用均拒绝同一包连取两次，第二次应拒
7不新造身份体系：管理员鉴权复用横切身份实现管理端点不出现第二套账号表；权限判定走既有角色

6.5 与现有件的对位（不用从零设计）

  • 角色模板的来源已有现成实现：gen_nats_conf.py 现在就在为每个成员生成 「只能发自己的心跳、收则放开」的权限白名单。动态化 = 把这套生成逻辑从「部署时写进配置」 搬到「注册时按需签发」，模板形状照抄，不用重新发明。
  • 多成员托管已是既成事实：本机一个守护进程托管 5 个成员身份（见第七节）， 所以入网服务要按成员粒度设计，不是按进程粒度 —— 否则同机的 5 个身份没法各入各的网。
  • 名册真源需要一次迁移：现在名册靠订阅心跳动态收集；目标的 /members 是登记库 + 心跳的合成视图，不能两套并存，否则「谁在网」有两个答案。
  • 通道侧需要一次性配置：签发侧需要通道服务端开一次「外部授权」开关并指向本服务 —— 实测通道服务端版本 2.14.5，满足外部授权方案的最低版本要求， 这条路在现网走得通，不必先升级（探测方式：只读连客户端口读服务端握手信息；日期 2026-09-25）。

6.6 失败模式与兜底

六种失败模式（引导包被截获 / 注册服务挂 / 伪装注册 / 重复注册 / 授权服务故障 / 版本漂移） 的逐条兜底见规划文档 6.2 节，本草案不重复。此处只加一条与台账相关的：version 漂移必须可观测 —— 台账登记每个在网成员的客户端版本，注册服务拒收低于最低兼容版本的申请，并写审计。

7.3 为什么「重启会掐断别人」

因为一个守护进程托管 5 个成员身份：为了给第 6 个成员加凭据而重启， 会把已经在网的 4 个成员的通道一起断掉。所以静态入网不只是「麻烦」—— 它把新增成员的代价转嫁给了存量成员。这一条是规划文档把它列为「第四处最痛耦合」的实证依据， 也是阶段 5 优先级的来源。

8.3 提示级命中的人判结论（今日）

  • 检查 2 的 48 行命中里，实质越层只有两处：成员 CLI 里的「会议召集」子命令 （业务语义长在通行层）—— 边缘端点里的「上下文自愈 / 会话头注入」已在阶段 1 刀 1+2 消解 （实现下沉到 L2 agent_usage.py），是本台账记下的第一处已消解越层。 其余多为文档字符串与帮助文本 —— 这也是它们只能是提示级的原因。
  • 检查 3 最该先收的一条：适配件里写死的运行时绝对路径（node 可执行文件路径）。 这条会直接阻断「换 OS 部署」，属于判据 6。
  • 检查 4 的 2 件越层：与规划文档「上下文水位三处口径」完全对位，见 4.2 的说明。

8.4 怎么用才不会变成形式

  • 硬门禁（检查 1）进提交前检查；提示级只在阶段收口时看趋势，不要为了清零而清零。
  • 每次拆件（阶段 1–5）后重跑，把 --json 结果按日期留档，用「越层数是否单调下降」 衡量重构是否真的推进 —— 比「代码更好看了」可核。
  • 门禁报的件名以层归属表为准；新增件必须先登记再写码，否则门禁看不见它。

九、待确认（每项附推荐默认）

#待确认推荐默认不定的代价
1层归属表里那 4 个「跨两层」的件，拆分点是现在就标注还是先跑通业务再拆？先标注、不拆（本台账已标）—— 标注零成本，拆分有风险，先把边界说清不标 = 每次讨论都重新吵一遍它属于哪层
2提示级命中要不要进提交前检查？暂不进，先只做趋势登记过早进 = 每次提交都在处理注释里的假命中
3入网接口的「人工批准」一环保留还是全自动？保留（管理员一次点击），但设计成可一键关掉的开关全自动 = 邀请码泄露即等于入网；永久人工 = 达不到你要的「零人工」
4引导包要不要包含通行层客户端件本身？包含（否则新节点仍要人工放文件），但包必须一次性 + 短时效 + 绑公钥不含 = 「自取文件」这一环落空
5名册真源切换（心跳收集 → 登记库合成）的时机阶段 5 内一次性切换，不留两套并存期并存 = 「谁在网」两个答案，排障时互相打架
6本台账与规划文档的关系，是否要合并成一份？分开：规划是稳定的「为什么」，台账是高频变化的「现状与工具」合并 = 每次改层归属都要动权威设计文档
7下一步先做哪期？阶段 1 抽适配层（台账已把越层点指出来，改动面最小、收益最直接）先做网关或通行层 = 动的面更大，回滚更贵
