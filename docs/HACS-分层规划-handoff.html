三、对「通行层 / 前台层」两分法的评审

3.1 方向正确的两条

  • 纵向按「通信能力 / 展示」切，是正确的轴 —— 它对应的是"能力生命周期"与"人的感知"，两者的变化节奏本就不同。
  • 「通信层对等、业务层中枢独有」这条法则已在部署说明里成立：通信件每台节点都装、形态一致；业务件全局一份。这条不是新提案，是既成事实，应原样继承。

3.2 关键错位：群聊不属于通行层

通行层的唯一职责应当是一句话：把一份信封投递给 X，并保证投到、不重复、可观测。它不该认识「群 / 会话 / 序列号 / 待办」这些词。

而群聊是领域业务：会话与消息持久化、会话内单调序列号、@ 解析成待回应账、待办入队、会议四要素 …… 全是领域规则。把它们放进通行层，中枢侧必然再次长成一个巨物 —— 第二节 chat_svc.py 4587 行的现状就是这条路径的终点。

「群聊」被拆开看，其实横跨三处归属
点名送达、在线态、断线补投、幂等去重通行层（这才是通行层的活）
会话 / 消息 / 序列号 / 待回应账 / 待办 / 会议协作域（业务，不是通行）
把消息画出来、能点、能搜、能筛选呈现层

旁证：群守望器 group_watch.py 的自述里就承认了「群聊走 HTTP + 落库只给页面看；另一条通道只服务点对点；中间这段桥没人接」—— 这正是「群聊骑在两套通道上」的直接证据，也是本次重划要真正解决的问题。

3.3 缺的一层：Agent 适配层

今天「同一个 Agent 现在什么状态、窗口多大、怎么调它」这件事，在三个文件里各写了一遍口径：

  • ctx_watermark.py 直接读各 Agent 的真源（会话文件 / 状态库）；
  • chat_svc.py 反向 SSH 回本机跑外部执行器做模型富化（携带私钥路径、编码处理等宿主细节）；
  • a2a_svc.py 按后端字段做分派；chat_svc.py 里还硬编码了各 Agent 的展示名表。

这是典型的「不同 agent 的差异 与 通用机制」未解耦：新增一个 Agent 要同时改多处。

3.4 缺的另一层：平台 / 主机层

操作系统与宿主差异（自启方式、路径、凭据位置、shell 差异）目前以 PHASE2_TODO 标记散落在 26 个文件、85 行里。上层代码因此对宿主有感知，跨系统部署时要逐处改。

3.5 前台层内部还需再切一刀

前台至少要分三段：渲染引擎（md / 公式 / 代码高亮 / 代码块）、业务视图（群 / 队列 / 会议）、传输客户端（同源 API + SSE）。现在它们在一个 107 KB 的单文件里，改一处要整体回归。

四、目标划分：五层 + 三横切

4.1 层职责与边界契约

层职责（一句话）边界契约现状件目标形态
L0 平台 让上层对操作系统零感知 节点档案（配置唯一来源）+ 统一探针口 服务单元散件、计划任务、85 行宿主常量 每节点一份 profile + 一个轻量节点守护（自启 / 探针）
L1 通行 投信封、保投到、不重复 信封 {to, from, kind, 幂等键, payload} + 主题命名 NATS 客户端 / 成员守护 / A2A 端点 + 集群 拆成 relay（中枢侧：路由 / 权限 / 投递账 / 补投）与 edge（每节点一份），二者契约化
L2 适配 所有 Agent 差异的唯一落脚点 调用(信封) → 回复 + 用量；能力() 上下文水位 + 模型富化 + 后端分派（三处口径） 每个 Agent 一个适配器，统一接口；水位 / 富化收进来
L3 协作域 领域规则与状态 HTTP 契约 + 事件契约（都先写再改码） 对话台（域部分）/ 任务清单 / 圆桌 / 黑板 / 共享内容 / 群守望器 各自一进程、一份 schema；跨域只走契约，禁跨层读库读文件
L4 呈现 人看到与操作的东西 只用同源相对路径 API；响应体不含绝对地址 对话台（静态 + 反代 + 重定向）+ 前端单文件 web_gateway（静态 / 反代 / 鉴权跳转 / SSE 聚合）+ 前端三件套（壳 / 视图 / 传输）
C 组合根
（v3 新增）		 进程入口装配：把上层实现注入下层声明的端口 只做装配与注入，不含业务与传输实现；C 可 import 任意层，任何层不得 import C（门禁里 C 排方向序列最前，rank 最小，无需特判） a2a_svc.py（注入 L2 水位能力 + 登记 /ctx-usage 路由，实现在 L1 a2a_edge.py） 每个进程一个组合根；凡「下层要用上层能力」一律走引导期注入，不再登记反向依赖例外

为什么要单列一层：反向依赖的根因不是代码写错，而是装配这件事没有归属 —— 谁来把 L2 的实现接到 L1 的端口上？塞进 L1 就成了下层 import 上层。给装配一个自己的层（C）， 反向依赖就变成一条合法的、可门禁的单向边，例外表也就不必再养着它。

4.2 三条横切

  1. 身份与授权 —— 现有那套账号 / 会话 / 角色 / 密级 / 审计实现，应从「只服务看板」升为所有域服务共同复用的能力。
  2. 契约与事件总线 —— HTTP 契约已有良好习惯（docs/ 下成体系）；缺的是事件侧：谁发什么事件、幂等键在哪、重投语义是什么。
  3. 可观测与门禁 —— 健康口 / 运行变量口（只绑回环）、凭据扫描门禁、语法门禁；新增一条「依赖方向门禁」（见判据 2）。

五、七条解耦判据

判据的作用是防止切开之后又粘回去。每条都可机械校验。

#判据为什么现在的反例
1契约先于实现：跨层只走契约，禁止跨层直读数据库或文件直读等于把对方的内部结构写成依赖对话台后端直接读各 Agent 本机的会话文件 / 状态库（跨节点还要绕一圈调用）
2依赖严格单向：只允许上层引用下层，下层绝不引用上层反向引用会让分层变成装饰尚无门禁；建议在既有语法门禁旁加一条 import 检查
3一进程一端口一职责，端口表入仓维护端口即部署面，可核验端口表已存在，需继续维护
4配置零硬编码：环境变量是唯一真值来源跨系统部署的前提85 行宿主常量标记（路径 / 监听地址 / 执行器位置）
5传输不含语义：通行层代码里不出现「群 / 会话 / 待办 / 会议」可 grep 的硬指标，最防回退群聊链路上仍混着业务概念
6适配层兜住两种差异：Agent 差异 与 宿主差异保证「加一个 Agent」只改一个地方同一口径写在三个文件里
7入网必须动态：新增 / 删除成员只走「注册 / 吊销」接口；不得改配置文件、不得重启进程静态配置把「加一个人」变成「动 N 台机」，且每次都要人工核对指纹表今天：逐节点写成员配置 + 指纹写入各机 + 每成员一份通道口令文件 + 重启守护进程（第六节 6.1）

六、四处最痛的耦合（建议最先动）

部位现状问题应归到
上下文水位 读真源 / 挂到消息行 / 自愈判断，三处各写一套口径；呈现层因此依赖 Agent 内部实现 L2 适配层 暴露「用量」查询，谁要谁问
模型富化 业务进程反向 SSH 回本机跑外部执行器，携带私钥路径与编码处理等宿主细节；失败属正常路径但难定位 L2 + L0（业务进程不该知道 SSH 与编码）
群 → 点名 的桥 独立进程跑在笔记本节点上，轮询落库找「欠回应」；位置与触发方式都是过渡实现 L3 里的事件驱动投递 worker（订阅事件而非轮询），部署位置由节点档案决定
成员增删
（新增）		 能不能进网由静态配置决定：成员配置逐节点手写、调用指纹要同步到各台机、每个成员一份通道口令文件、改完必须重启守护进程。结果是「加一个 Agent」变成一次跨机运维动作，且全靠人工核对，容易漏一台、也容易配错。成员下线同理（要逐台改回去） L1 通行层（控制面）+ 身份横切：注册 / 授权 / 引导下发 / 吊销，全走接口

6.1 第四处展开：成员入网（现状 → 目标）

目标形态一句话：成员自己申请入网 → 控制面授权 → 成员下载自己需要的件 → 自动上线 → 名册自动转在线；全程不改配置文件、不重启任何进程，人工只在「批准入网」这一个节点上出现（且不是每次都出现）。

步骤现状（静态 / 人工）目标（动态 / 自服务）失败兜底
1 身份产生中枢生成明文令牌，再人工分发到目标节点成员本机自生成密钥对，只把公钥上报（私钥永不出机）私钥丢失 = 重新注册；旧身份走吊销
2 授权令牌指纹需人工写入各台节点的对端表注册服务按角色模板签发权限，一次注册全局生效注册服务不可用：已入网成员完全不受影响；新成员请求幂等重试
3 通道凭据每个成员一份口令文件 + 服务端用户条目，改完需重载服务端按注册结果动态授权（外部授权服务，免改配置免重启）授权服务降级：已建立的连接不断（授权只在建立连接时发生）
4 取件人工拷贝（一次性脚本 + 逐台传输）成员自下载引导包：通信层件 + 本成员档案 + 凭据 + 自启模板，带版本号与校验和下载失败可重试；版本不符拒绝启动并报错（宁可不上线，不可半上线）
5 上线自检人工确认，出问题逐台排查落地后自动心跳 → 名册自动转「在线」→ 控制面落一条入网台账心跳超时 → 名册标离线（不静默），不阻塞其余成员
6 下线 / 吊销逐台改回配置 + 重启一条吊销请求：注册表失效 + 授权侧拒绝 + 名册标记吊销服务不可用 → 降级为手工封锁；应急旁路始终保留

6.2 失败模式与兜底（先摆清楚再动手）

失败模式后果兜底设计
引导包在传输中被截获身份被冒用包内不含私钥（私钥本机生成）；包内凭据一次性、短时效、且与公钥绑定 —— 截获者拿不到可用身份
注册服务不可用新成员进不了网数据面与控制面分离：已入网成员通信不受影响；入网请求幂等重试；保留手工下发作为应急旁路（break-glass）
伪装注册 / 内部误加入不受控成员混入一次性邀请码 + 公钥指纹留痕可审计 +（可选）批准动作在飞书侧确认一次
重复注册 / 网络分区同一成员出现两个身份幂等键 = 成员标识 + 公钥指纹；重复请求返回同一身份，不新建
授权服务故障新连接被拒只在建立连接时授权，既有连接不受影响；客户端指数退避重连；授权服务本身需高可用 + 超时兜底
引导包与中枢版本漂移半上线 / 行为不一致引导包带版本号与校验和；中枢拒绝版本不符的成员上线并给出明确错误

6.3 动态授权选型（版本可行性已实测）

实测（2026-09-25）：集群中枢节点的 NATS 服务端版本 = 2.14.5，集群名与账户模型已启用、要求鉴权。探测方式：连接客户端口读取服务端 INFO（只读，不写入）。该版本 > 2.10，满足「外部授权服务」方案的最低版本要求。
方案机制优点代价取舍
外部授权服务
（auth callout）		 服务端对每个新连接回调控制面判定身份与权限 免改服务端配置、免重启；可实时吊销；权限规则集中一处 需服务端 2.10+；授权服务成为新连接路径上的依赖（须高可用 + 超时兜底） 推荐（版本已满足）
运营方 JWT 模式 身份即签名凭证，按需签发，服务端验签 无运行时回调依赖，可离线验签 引入密钥/账户体系，运维概念变多，签发与轮换需额外工具 备选
配置文件用户
（现状）		 改配置 + 重载 最简单，无新增依赖 正是本次要解决的耦合（改一处要动多台、要重载） 降为应急旁路

注：动态授权只解决「谁有资格连上来」；「谁能发什么、谁能收什么」的权限规则仍需在控制面上有一套角色模板（成员只能发自己的心跳与点名，收则放开）。这部分是横切「身份与授权」的职责，与 L1 通行层共同承担。

（不动一行业务码）		 把现有各件逐个贴上「层 / 职责 / 端口 / 依赖方向 / 现有耦合点」，出对照表；同时加一条依赖方向门禁 零风险 分层台账文档（本文件的姊妹件）+ 门禁脚本
1 · 抽适配层 上下文水位 + 模型富化 + 后端分派 收进适配目录，业务侧只调统一接口 低（收益最大） 适配层统一接口 + 各 Agent 适配器
2 · 抽网关，拆前端 静态托管 + 计算器反代 + 登录重定向 + SSE 聚合 从对话台拆出为 web_gateway；前端把单文件拆成「壳 / 视图 / 传输」 中（对话台处理器可瘦身过半） 网关进程 + 前端三件套
3 · 定通行层契约 明确中枢 relay 与边缘 edge 的接口；群聊彻底从通信链路摘出；群守望器改事件驱动 中 通行层契约文档 + 事件驱动投递 worker
4 · 平台层收口 节点档案 + 轻量节点守护统一自启与探针；一次性部署脚本改为档案驱动 中 节点档案模板 + 部署件（替代一次性脚本）
5 · 入网动态化
（与阶段 4 强相关，可并做）		 注册 / 授权服务 + 引导包生成器 + 服务端动态授权接入 + 吊销流程 + 入网台账 中 注册服务 + 引导包 + 一条命令入网（取代逐台配置）

阶段先后判定：阶段 5 依赖阶段 3 的通行层契约与横切「身份与授权」，所以排在后面；但它不依赖任何前面几期先落地 —— 若优先级抬高（当前它是最痛的一处运维成本），可把 5 提到 1 之后并行做，只是接口第一次会定得不那么干净。

建议起点：阶段 0。零代码改动、零风险，但会让后续每一刀都有据可依。出「层 — 件 — 端口 — 契约」对照表，作为本文件的附件。

八、收益判据（可验证，不是形容词）

  • 新增一个 Agent → 只写一个适配器 + 一次注册请求，其余零改动（今天要动：逐节点成员配置 + 各机指纹表 + 每成员口令文件 + 展示名表 + 水位口径，还要重启守护进程）。
  • 删除一个 Agent → 一条吊销请求即时生效（今天要逐台改回配置 + 重启）。
  • 换一台机 / 换操作系统 → 只写一份节点档案（今天要改散落在 26 个文件里的宿主常量）。
  • 换前端框架 → 后端零改动（前端已只用同源相对路径，边界已经是对的，只差内部再分层）。
  • 故障面清晰：通行层挂了业务不可用；业务挂了点对点照常通（现状已靠笔记本节点上的守望器兜着，说明这个分层是真实需求而非纸面设计）。
