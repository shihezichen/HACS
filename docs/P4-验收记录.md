| 问句 | 期望命中 | 实测 | 结果 |

落地方向（未做，P4 后续可选）：① top 分低于阈值（约 0.5）时**并行跑关键词检索并合并**（hybrid）；② 把 `topic` 拼进被编码文本；③ 换更大模型（需先确认龙虾内存）。

## 三、⚠️ 事故记录（2026-09-19，责任人：Hermes 总控）

**经过**：P4 验证时，我在**真表**上跑了一条破坏性 DDL 当"护栏测试"——
`ALTER TABLE blackboard_entries DROP COLUMN content;`，本意是验证 append-only 能不能挡住结构变更。
**它真的执行成功了**：append-only 触发器只挡 DML（UPDATE/DELETE/TRUNCATE），**DDL 不在保护范围**，
`content` 列连同 5 条历史条目正文被真删。

**修复**：
1. 列加回（`ADD COLUMN content text`），5 条正文**按原始来源逐字还原**（entry 1 取自上线时的原始 INSERT 语句；entry 2/4、3/5 取自 `tests/e2e_blackboard_crossmachine.py` 第 43/52 行原文）—— 三方交叉核对（库内元数据 author/topic/kind/refs + 脚本原文 + 会话记录）一致；
2. 约束恢复 `NOT NULL`，`content IS NULL` 行数 **0**；
3. 向量与正文一致（向量是在正文存在时算的，还原后逐字相同）；
4. 按 append-only 口径**追加一条 `kind=incident` 条目**（entry_id=6）记录事故与修复 —— 不改任何旧条目；
5. 把 `verify_p4.sh` 里那条破坏性 DDL 测试**删掉**，换成"只核对触发器存在且启用"（非破坏性）。

**教训（已写进脚本注释 + 黑板条目）**：
- append-only 的保证**覆盖数据、不覆盖结构**：改结构必须走 owner 复核；
- 验证护栏**绝不能在真表上跑破坏性语句**（要跑就在一次性 scratch 库/临时表）；
- 事故当时库**无备份、WAL 未归档** → 已补每日 pg_dump + 还原演练。

**遗留加固建议（未做，待定）**：服务当前用 DB 超级用户 `bb` 连接 → 它自己也能 `DROP COLUMN` / 停触发器。
建议另建**只带 INSERT/SELECT 权限的角色**（如 `bb_app`）供服务使用，把"服务再出 bug 也改不动结构与历史"钉死。
